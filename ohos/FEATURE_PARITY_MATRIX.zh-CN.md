### 不能跳过的流水线依赖

原版 `ScriptViewModel.UpdateThread` 并非只有插值。其核心关系为：

1. 配置设备轴和上一次轴状态 → 媒体位置/全局及每轴 offset → 脚本索引、首尾和间隙判断。
2. 脚本插值/缩放/反转、Motion provider、外部 transition 三条支路分别计算并应用 bypass。
3. 按规则选择/混合有效值 → auto-home → soft-start sync → smart limit → speed limit。
4. 保存 dirty/speed/状态、发布轴事件 → 每个输出独立的启用与范围映射 → update context 节拍/事件策略 → 协议序列化 → 传输。

当前 OHOS 主要覆盖第 1 项的时间公式、第 2 项的脚本变换和模拟安全门。**不要直接把 `previewSamples()` 接 Socket 就称完成移植。** 依赖轴读取时采用上一周期还是本周期的状态、首次无有效值、空脚本、末帧之后，均须用固定轨迹对照原版；单独公式正确不足以证明组合正确。

### 当前有意或实际存在的兼容差异

1. OHOS 输入校验更严：动作时间要求整数毫秒、0–24h，位置0–100；原版 reader 可接受小数时间、忽略负时间、钳制位置。某些原版可读文件因此会被拒绝。
2. 原版只把已启用/已知设备轴放入多轴结果；OHOS 直接导入模型可接收更宽泛轴名，资源匹配又采用默认启用轴。应统一设备模型，不能凭“更多轴名可解析”宣称更兼容。
3. 原版嵌入重复轴 ID 会字典覆盖，OHOS 拒绝重复轴（包括 `actions` 与嵌入 `L0`）；需要明确兼容策略。
4. ZIP 边界、路径安全、排序比较器、目录授权/遍历上限与 Windows 不相同。完整列表见 [LIBRARY_MATCHING.md](LIBRARY_MATCHING.md)。当前规则不是无上限的 Windows 文件系统镜像。
5. 合并文档只保留一组元数据；当前热力图/章节和轴页的关系不等同于原版各 `IScriptResource` 的资源模型。
6. 曲线/偏移/缩放等编辑会暂停播放，新文件重置轴设置。原版有持久轴设置和 soft-sync；这是安全原型的行为差异，不应静默算作完全相同。
7. Native seek/buffering/音频中断后需明确重新播放；后台释放视频后需重新打开。没有持续后台播放/自动恢复承诺。
8. Windows 程序/命名管道/RawInput/XInput/C# 插件需平台适配决策；标记“待适配/不支持”可以诚实，但不能从清单中消失。

1. 完成 U01–U06 的资源入口/视频呈现改动，保留真实 AVPlayer 时钟、单 surface 所有权和取消/后台门控。
2. 定义并真实验证公共 Download 访问；权限/API/设备条件不满足时，给出清楚的状态和最小必要操作，不返回伪造空列表或改扫别处。
3. 修复后全量测试、实际 ArkTS/资源编译、HAP 包检查；至少一台目标设备验证本地加载→匹配→播放→seek→改参数→全屏/返回→重进应用的闭环。
4. UI 连接/输出/实现状态真实；不得把禁用按钮启用成没有后端的占位功能。

### P1：支撑功能完整性的公共模型

1. **设备/配置轴模型 + 持久化**（E05/E06）先于全轴、Link、Motion、输入/输出映射；否则不同模块各自硬编码轴，越补越不一致。
2. **完整轴状态流水线**（B12、C06–C18）先于物理传输。先以可控时钟和合成轨迹测试最终值、状态和事件，再接输出。
3. **Internal 播放列表 + 单轴脚本资源管理 + AB/自动跳过**（A04/A18/A19/B11）依赖统一资源/时间/每轴 metadata 模型；不能只补四个按钮。
4. **原生时间与生命周期实测**（A20/A21/C19），确认观测节拍、seek 和渲染生命周期；在此基础上制定允许的同步误差，而不是凭理论宣称毫秒级。

### P1/P2：输出与外部集成，逐个完成闭环

1. 先做输出通用模型/范围、TCode 编码、update context、连接与安全门（D01–D04/D13/D14），用本地假接收器验证字节、节拍、取消和重连。
2. 选择用户实际需要的一个网络输出与一个远程源，完成从媒体时间到接收器的端到端验收；随后逐项扩展 TCP/UDP/WebSocket/Buttplug/Handy 等。完成一个不能把其他类型一起改成完成。
3. 跨设备/串口/Handy 的真实动作只在明确设备与授权后进行。Windows 专属项目先报告可行方案/限制，不能据此静默跳过功能。
4. Remote repository、路径修改器、完整快捷键需共用媒体/轴/动作模型；可分批接入，但各自需要接口与真实行为测试。

### P2：完整界面与维护能力

- 完整热力图预览/标记条、数字编辑、弹层、状态灯、主题、General、信息/诊断、输入配置及插件替代方案。
- 手机/平板/PC共享同一个业务状态，不做三份简化引擎；桌面鼠标专用操作提供触摸等效入口。
- 根据 [UI_PARITY_AUDIT.md](UI_PARITY_AUDIT.md) 做同状态视觉/交互对照；深色、窄屏、多轴、多输出、全部展开、长文件名、错误/空状态都需要截图。

## 10. 每个功能改为“完成”的最低证据

- [ ] 指定原版符号/行为与目标范围，写清平台差异；不存在“按钮已放上”结项。
- [ ] OHOS UI → 模型 → 算法/适配器的真实调用链接通；错误、取消、重复操作与旧回调覆盖。
- [ ] 单元/集成回归（必要时黄金轨迹/黄金字节）；最终变更之后重跑，报告通过、失败、未运行三类结果。
- [ ] 原生 API 的目标设备验证：机型、系统/API、权限条件与操作记录；编译警告/能力声明不是实机证据。
- [ ] 前后台、窗口/旋转/全屏、断开/恢复不丢所有权、不意外恢复运动。
- [ ] 如有持久设置：杀进程重启/升级/损坏配置回退；权限与密钥独立安全处理。
- [ ] 矩阵记录修复 SHA 与验证结果；缺项保持可追踪，禁止用整体“功能齐全”覆盖尚未完成的行。
